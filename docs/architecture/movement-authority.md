# Movement authority and intended turn steps

The client chooses a direction and the movement revision on which it should first take effect. The server owns time budgets, legal trajectories, collisions, apples, damage, death, progression, and all effects on other players. Predicted bodies are presentation state only and always contain integer grid cells.

## Commit contract

The browser advertises `turnSteps=1` and completes the existing prediction/resume handshake. The transport enables `MovementTurnAuthority` on the session queue before the welcome snapshot. The server delays that player's movement commits by **120 ms** (an 80 ms input budget plus 40 ms of clock uncertainty), once at initialization or after a movement hold. This does not change their movement interval. A nominal step due at 100 ms commits at 220 ms, subject to the existing 20 ms action scheduler. The client displays that step at its nominal due time.

`setDirection` carries a monotonically increasing connection-local `inputSequence`, `intendedRevision`, and `estimatedServerTimeMs`. It carries no position. The predictor advances to the input timestamp before assigning the revision, so pressing immediately before or after a movement boundary selects different steps. The shared two-turn queue determines whether the direction belongs to the next step or the buffered following step. Replacing a buffered turn replaces the pending direction for that revision on the server as well.

The server accepts only uncommitted, ordered, bounded revisions. The upper bound is the committed revision plus the number of nominally due steps plus two queue slots. Timestamp plausibility allows 40 ms of clock uncertainty and at most 120 ms of input age; this never reopens a committed revision or extends the 120 ms commit delay. A timestamp inconsistent with the claimed step is rejected, with one scheduler tick of boundary uncertainty. Input buffers are capped at 64; duplicate sequences cannot add steps. These estimates are evidence for input acceptance, never authority to advance simulation time.

The authority retains at most 32 timestamped interval changes. Validation uses the cadence at the estimated input time, so a legitimate turn recorded before a speed update is not judged solely against the new interval. The authoritative scheduler still determines every actual movement step. Matching already displayed prefixes can survive a cadence update without rewinding their grid geometry.

At the intended revision, the session submits the direction through the existing `SnakeGame.handleCommand` / `SnakeState` direction queue, then executes the normal `stepPlayerAction` once. Reversals, traversal locks, body and obstacle collisions, speed modifiers, pickups, damage, survival, death and rewards use the canonical server rules. An acknowledgment means the input has been consumed at commit, including an input rejected by canonical direction legality. `movement.turn-applied.reason` distinguishes these outcomes. Untimed forced steering is rejected during automatic movement; the existing server-issued manual traversal resume state remains supported.

There is **no rollback of committed world state**. A valid turn delivered during grace can avoid an impending collision because that step has not executed. A turn delivered after commit is rejected, even if its claimed timestamp predates a collision. Existing lethal-step safety holds remain their own gameplay rule. Other players and moving world objects are checked in their current authoritative state when the step commits, in the existing session/player ordering. No speculative apple, damage, death or reward is broadcast and later undone.

## Clock and phase

The application-level `movementClock` exchange echoes the browser's monotonic send timestamp alongside simulation time. All movement timestamps read the fixed authority clock owner, independent of the active player context, and a late join receives that shared time before its first environment update. While the real simulation timer runs, probe timestamps include the fractional time since its last update, capped at 20 ms; paused clocks do not extrapolate. This removes the previous-tick bias without granting movement steps. The browser retains eight RTT/offset samples, selects the lowest-RTT sample to reduce queue/jitter bias, and probes once per second. RTT above one second is discarded. A received authority timestamp is a lower bound on the estimate; old probe replies cannot pull time behind a newer snapshot. Paused/clamped simulation discontinuities and replication epoch changes invalidate stale clock estimates, including in-flight samples sent before a hold. Offset estimates and their uncertainty are diagnostics, not a security credential.

`movementAccumulatorMs` exposes the player's nominal phase: the commit accumulator plus grace plus the action scheduler's fractional accumulator. `movementPhaseAtMs` timestamps that phase. The existing snapshot lane always carries both values atomically, even when the phase number repeats across a fast-lane movement step; the predictor also rephases immediately when a clock probe resolves. **Phase can exceed one movement interval while commits are pending.** Consumers must replay whole due grid steps and keep the remainder rather than taking the value modulo the interval and losing revisions. This covers intervals such as 50, 70, 100, 126 and 200 ms without assuming that 20 ms divides the interval. The server recomputes the real interval after each movement step; a speed change never grants extra client-created time.

The predictor retains unacknowledged input sequences while the server's uncommitted prefix catches up. Matching authoritative prefixes retain valid displayed movement. Uncertain collision geometry stops speculative display while connected next-step steering remains available; it cannot backdate a decision into the blocked nominal step. Invalid trajectories and actual authoritative relocations correct to exact cells. Domain-command delta replies include a current movement resync so their timestamp and movement phase describe the same state. Normal world publication stays at 100 ms; immediate movement publication and the periodic one-second movement resync remain in place. No local or peer interpolation is introduced.

## Reconnect and holds

The existing token-bound reconnect mechanism still validates published revision history and elapsed server time, caps speculative replay, and executes normal authoritative steps against the current world. Suspension clears pending connected-turn plans before input-only replay, preventing double application. Reattachment resets the connection's input sequence fence without adding another grace delay. Holds, respawn and world reload discard pending turn plans. Delayed packets from superseded sockets cannot act for the new connection.

An early reconnect retains a negative remaining commit accumulator rather than rounding it up to zero. Replay step budgets are clamped to zero while that delay remains; reconnecting cannot skip the original commit window or manufacture movement time.

## Diagnostics

`GameConnection.getMovementDiagnostics()` is included in manual/periodic scene debug snapshots as `movementAuthority` and in the development browser bridge's `getPresentation().movementDiagnostics`. It exposes intended and server-applied turn revisions, current authority revision and interval, estimated clock uncertainty, phase error, RTT-derived input latency, current/maximum frame gap, correction magnitude/count/maximum, correction reason, and the last input rejection. Frame gaps help separate browser stalls from step-selection errors. The `movement.turn` and `movement.turn-applied` server diagnostics record sequence, intended/applied revision, estimated input age and concrete validation/legality reasons. Negative estimated input age indicates clock uncertainty rather than negative network latency.

## Verification and measurements

Run `npx tsx scripts/benchmark-movement-turns.ts` for the deterministic before/after comparison. Both paths use the real authoritative scheduler and predictor with identical inputs: five intervals, turns at boundary minus/plus 1 ms, and arrival delays of 0, 15, 35 and 65 ms. The baseline disables the new grace/step protocol and uses the original arrival-time direction path. This measures trajectory disagreement, not rendering or Internet throughput. Correction magnitude is maximum segment Manhattan distance at the intended revision.

The existing real-socket throughput benchmark was also run on the original checkout and after implementation, using its unchanged legacy-client workload. It is a publication/transport regression check, not a step-aware latency benchmark. World packets were 56 at every interval before and 58/56/56/56 after; the 50 ms run captured one additional two-client publication cycle. The configured 100 ms world cadence is unchanged. Movement packet counts stayed 212/166/110/74 at 50/70/100/200 ms. Mean command acknowledgments were 1.26/0.94/0.95/1.07 ms before and 1.20/1.03/1.28/1.31 ms after. Timestamped phase metadata increased total payload by approximately 3.5–7.1%, including that extra cycle in the fastest run. Raw [before](benchmarks/movement-network-before.json) and [after](benchmarks/movement-network-after.json) samples retain delivery/build timings.

`movementTurnAuthority.test.ts` covers boundary timing, five speeds, delayed/jittered inputs, buffered replacement, clock skew/stalls, speed changes, wall/peer collisions, authoritative death, single pickup rewards, duplicate/future/old inputs, reconnect replay and protocol validation. Existing movement/reconnect tests remain active. `movementTurns.smoke.spec.ts` runs two Chromium clients with ordered socket delays cycling through 15/35/55 ms, five live speed changes, exact intended/applied revision assertions, and integer-body/zero-correction samples. The existing discrete movement browser test additionally checks lifecycle reconnect and authoritative relocation. Browser runs save a screenshot and the jitter test attaches movement diagnostics.

The measured boundary-race workload has zero trajectory disagreements with the new protocol. This is a bounded guarantee: arrivals after commit, unknown geometry, changed server speed/world state, invalid inputs and long stalls still require authoritative correction. Arbitrarily asymmetric network delay cannot be inferred exactly from RTT; grace does not grant historical invulnerability or unlimited lag compensation.
