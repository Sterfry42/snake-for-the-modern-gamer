# Short movement reconnects

The authoritative session remains the only gameplay writer. `ClientMovementPredictor` owns a separate local-snake presentation projection; it never calls `SnakeGame.actionStep()` or changes `SceneReadReplica`.

## Suspension and resume

An unexpected socket close suspends its character for 3,000 ms. The existing connection presence remains visible with `suspended: true`; automatic player movement and per-player subsystem clocks stop, while world clocks and other players continue. Interaction, minigame, vehicle, progression, direction queue and movement accumulator state are retained. Reattaching an opaque resume token during that window replaces the connection without leave/join notices. Explicit Leave server uses close code 1000 and performs normal cleanup immediately. On timeout, the normal disconnect cleanup runs and announces departure. An expired token can still resume its retained character, but cannot catch up movement.

A live-socket replacement also preserves the character and subsystems. The old connection cannot execute commands, detach the replacement, or reuse its catch-up attempt.

## Timing and inputs

Player snapshots include a monotonic `movementRevision`, `movementIntervalMs`, `movementAccumulatorMs`, and the shared two-turn direction queue. The local player also receives grid dimensions and `movementPredictionAllowed`. The revision advances for each authoritative movement-clock action, including safety holds; world loads and respawns invalidate old revision bases.

The transport runs the same isolated local movement projection during connected play and reconnects. Connected presentation uses a stable server-tick anchor plus the authoritative movement interval/accumulator; publication jitter does not restart the local movement clock. Projection of delayed snapshots is capped at 250 ms. Direction commands include an optional bounded `inputSequence`; snapshots echo `acknowledgedDirectionSequence`, so only unacknowledged turns are reapplied during reconciliation. These numbers acknowledge inputs and grant no authority. `snakeDirectionQueue` is shared with `SnakeState`, preserving buffered turns and reversal rejection. Cached room geometry bounds speculation: solid tiles, water, self collisions, unknown rooms, manual areas and special traversal stop speculative advancement. One cached coordinate-room boundary can be crossed; replay then returns control to normal authority. No terrain is generated and no rewards, damage, pickups, NPCs, bullets, scores or interactions are simulated locally.

Protocol version 5 prediction clients advertise `prediction=1` and send one `movementResume` hello before welcome. A bounded replay contains the previous connection ID, base movement revision, predicted step count, elapsed duration and ordered cardinal direction inputs at step offsets. It contains no claimed position. The server binds this to the token's suspended player and validates the old connection, base revision, grace deadline, cardinal inputs, ordered offsets, input count, elapsed-time budget and 30-step cap. A base must match current authority or one of the last 160 revisions the transport published for that connection within three seconds. If authority advanced after publication but before suspension, those already-applied steps are subtracted and inputs are rebased onto current authority; they are never executed twice. Future, unpublished, grossly over-budget and invalidated world/respawn bases are rejected. A bounded connected prediction lead is clipped to actual server elapsed time rather than discarding the entire valid prefix; capped steps are reported and never executed beyond that budget. Only revision numbers/timestamps are retained, not historical world state. Missing or stale catch-up falls back to normal authoritative resume. Other commands are rejected during reconnect; they are never queued. Direction inputs arriving after the hello are bounded and handed to the live connection after welcome.

Accepted catch-up runs through `stepPlayerAction` and the real gameplay path against the current world. Death, a safety hold, a changed room, a forced interaction, lost health or a movement discrepancy stops the replay. Existing wall safety grace is preserved rather than burned through in a burst. Replay events are captured before attachment and delivered after welcome, so authoritative death/revival and gameplay feedback still reach the returning player. There is no world history or rollback.

## Reconciliation and limits

Prediction lasts at most three seconds and 30 movement steps without fresh authority. The hello freezes its submitted projection until welcome; a failed handshake can continue the original bounded window. The predictor retains its displayed connected state at suspension rather than jumping back to the previous snapshot. A matching authoritative prefix preserves already displayed steps and phase. A mismatch takes an exact authoritative grid state and replays only relevant buffered directions; no correction blends positions. Death, holds, manual areas and unsupported geometry take authority immediately.

`PeerMovementPresentation` presents the latest authoritative grid body immediately. There is no immediate grid-aligned peers, presentation delay, or speculative peer gameplay. `PlayerHoldSynchronizer` still retries mismatched holds at most every 500 ms. The dedicated movement stream updates presentation and authoritative body selectors without full snapshot cloning or hydration. See [discrete movement stream](movement-stream.md) for packet ordering, acknowledgments, variable speeds, reconciliation and benchmark results.

Client error and handshake-timeout closes use application code 4000; only deliberate Leave/client shutdown uses 1000. Superseded clients use 4001 and protocol rejection uses 1008. A transport failure therefore takes the suspension path even when initiated by the browser's error callback.

The party indicator delays its reconnect notice by 350 ms, then shows a small reconnecting message. Exhausted or blocked prediction, or a three-second outage, shows that movement is waiting for the server. Automatic connection retries continue after prediction stops.

## Verification

`movementReconnect.test.ts` covers suspension, peer/world continuity, retained UI holds, real-socket grace expiry, timing phase, shared rapid-turn semantics, stale/foreign/expired/time-inflated replays, collisions against the current world, authoritative death, cached static geometry, replica isolation, prediction caps, and small/large grid corrections. The persistent-party browser suite breaks a real socket, enters direction input, observes continued local presentation while authority is stationary, and verifies authoritative catch-up and unchanged identity. Existing gameplay, party and transport suites remain active.

`movementReliability.test.ts` additionally checks connected cadence under publication jitter, input acknowledgement, lost-hold retries, immediate grid-aligned peers, published-base rebasing, movement/hold telemetry and asynchronous autosave ownership. The two-live-player browser case drops one resume-from-menu command, verifies retry/acknowledgement, then forcibly destroys one transport while the other player continues moving and checks completed replay without detachment.

A suspension/replay attempt is scoped to its server process and connection. Character identity and pending encounters additionally survive the last successful hosted checkpoint across process restart. A network failure is handled once the WebSocket reports closure; this slice does not add a new failure detector for connections that remain silently open.

Browser visibility alone does not close a socket or pause authority. `pagehide` reports bounded lifecycle context and closes with application code 4002, allowing a bfcache page to release its socket while retaining character grace. `pageshow` resumes the same credential. Going-away close 1001 and lifecycle close 4002 are identified separately from abnormal transport close, heartbeat timeout, backpressure and socket errors in server logs. Listener cleanup is owned by the connection. Initial connection rejection and actual server/queue failures retain their existing explicit error paths.
